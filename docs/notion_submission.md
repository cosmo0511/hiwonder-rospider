## 2. 과제 목표

### 해결하려는 상황

사람이 RosPider 를 **WASD 로 원격 조종**해 실내를 걷게 한다. 조종자는 로봇에 달린
카메라 화면만 보고 있고 로봇의 발밑은 보지 못한다. 이때 로봇은 조종자가 앞으로
몰더라도 **부딪칠 것 앞에서는 스스로 멈춰야** 한다. 동시에 **넘어갈 수 있는 2 cm 턱
앞에서는 멈추면 안 된다** — 그때마다 멈추면 조종 자체가 불가능해지기 때문이다.

로봇이 매 순간 답해야 하는 질문은 하나다:

> **지금 앞으로 가도 되는가?**

이 판단이 틀리는 방향은 양쪽 다 나쁘다. 못 멈추면 부딪치고, 아무 데서나 멈추면
쓸 수 없다. 그래서 "장애물이 있다/없다" 가 아니라 **"넘어갈 수 있는 것과 부딪칠
것을 구분" 하는 문제**다.

### 왜 센서 융합이 필요한가

**뎁스 카메라만으로는 안 된다.** RosPider 의 뎁스 카메라는 몸통이 아니라 **팔 끝
(link4)** 에 달려 있고, 관측 자세에서 전방을 **24.2도 아래로** 본다(URDF 에서 계산).
그래서 화면 아래쪽은 **언제나 바닥**이다. "가장 가까운 뎁스" 로 장애물을 찾으면
바닥이 1등으로 잡힌다.

현장에서 흔히 쓰는 대응은 화면 위쪽만 잘라 쓰는 것이다(고정 ROI). 세워 놓고 시험하면
잘 돌아간다. 그런데 **걷기 시작하면 무너진다.** 6족 보행은 세 다리씩 번갈아 딛으므로
지지 다각형이 매 반주기 바뀌고, 몸통이 보행 주기에 맞춰 계속 끄덕인다. 몸이 숙여지면
잘라낸 영역 안으로 바닥이 들어온다. **화면의 어느 부분이 바닥인지가 매 프레임
달라지므로, 화면 좌표에 고정된 규칙은 원리적으로 성립할 수 없다.**

**IMU 가 그 구멍을 메운다.** IMU 는 거리를 못 재지만 **중력 방향**을 안다. 중력을
알면 뎁스로 복원한 점마다 "이 점이 바닥에서 몇 cm 높은가" 를 계산할 수 있고, 바닥을
화면 좌표가 아니라 **기하학적으로** 제거할 수 있다. 그리고 높이를 알면 위의 요구가
바로 풀린다 — **높이 3 cm 이하는 넘어갈 수 있으므로 장애물로 세지 않는다.**

### 센서 선택과 역할

| 센서 | 출력 | 역할 | 이것이 없으면 |
|---|---|---|---|
| Depth | `distance_to_image_plane` | 전방 물체까지의 **거리**와 모양 | "얼마나 가까운가" 를 못 잰다 |
| IMU | `projected_gravity_b` | 몸체 **자세**(중력 방향) | 뎁스의 어느 점이 바닥인지 모른다 |
| IMU | `lin_acc_b` | **충격** | 이미 부딪쳤는지를 카메라로는 못 본다 |

두 센서는 화면을 나란히 놓는 데서 그치지 않고 **하나의 판정 변수로 합쳐진다.**
IMU 가 뎁스 점의 좌표계를 중력에 정렬시키고, **정렬된 좌표에서만 거리 판정이
일어난다.** 둘 중 하나를 빼면 파이프라인이 끊긴다.

`projected_gravity_b` 에서 얻으며 이 값은 `gravity_bias` 와 무관하다.

## 4. 구현 방법

### 4.1 데이터 수집 과정

매 물리 스텝(120 Hz)마다 시뮬레이션이 진행되고, **6 스텝마다(20 Hz) 판정**한다.
실기 뎁스 카메라가 30 Hz 인 것과 같은 자릿수로 맞춘 것이다.

```python
depth      = scene["camera"].data.output["distance_to_image_plane"]  # (N,H,W) [m]
intrinsics = scene["camera"].data.intrinsic_matrices                 # (N,3,3)
imu        = scene["imu"].data                                       # projected_gravity_b, lin_acc_b
```

**외부 파라미터를 매 스텝 다시 계산한다.** 카메라가 팔 끝에 달려 있어 팔이 움직이면
`R_cam←imu` 가 바뀌기 때문이다(joint3 을 0.4 rad 만 움직여도 행렬 성분이 0.385 바뀐다).

```python
q = ext.arm_joint_dict(joint_names, robot.data.joint_pos[0].cpu().numpy())
r_cam_imu = ext.r_cam_imu(q)   # URDF 체인을 런타임에 풀어서
```

> 이것이 꼼수가 아닌 이유: **실기도 똑같이 한다.** 팔 조인트 각도는 서보 엔코더
> (`joint_states`)로 알 수 있고, URDF 로 tf 를 계산해 카메라 자세를 얻는다. 여기서
> 읽는 `robot.data.joint_pos` 가 그 엔코더에 해당한다. 시뮬레이터의 정답 포즈를
> 가져다 쓰는 것이 아니다 — 그걸 쓰면 IMU 가 필요 없어져 과제가 성립하지 않는다.

### 4.2 단위·좌표계·측정 시점

| 항목 | 값 |
|---|---|
| 뎁스 | `distance_to_image_plane`, 단위 **m**, 카메라 광학 **z축** 기준 |
| 측정 실패 픽셀 | `inf` (`isfinite` 로 걸러냄) |
| 카메라 광학 프레임 | ROS 규약 — **+X 오른쪽, +Y 아래, +Z 시선** |
| IMU 프레임 | `imu_link`. base_link 대비 **yaw −90도** |
| 중력 | 단위벡터(크기 1) |
| 가속도 | m/s² (운동가속만, 중력 제외) |
| 각도 | 내부 계산 rad, 출력 deg |
| 로봇 몸 좌표 | base_link — +X 전방, +Y 좌측, +Z 상방 |
| **측정 시점** | 두 센서 모두 `update_period=0` → **같은 물리 스텝에서 읽는다. 시점 차이 0** |

> 측정 시점을 0 으로 맞춘 것은 시뮬레이터라 가능한 일이다. **실기에서는 IMU 가
> 수백 Hz, 뎁스가 30 Hz** 라 몸이 빠르게 끄덕이는 구간에서 뎁스 한 장 안에 자세가
> 변해 롤링 왜곡이 생긴다. 한계 항목에 적었다.

### 4.3 융합 흐름도

```
 ┌─ 뎁스 (N,H,W) [m] ──► 역투영 ──► 점 집합 p (카메라 광학 프레임)
 │        intrinsics K          x=(u-cx)/fx·z, y=(v-cy)/fy·z, z=depth
 │                                              │
 │                                              ▼
 │                         h = p·up − (바닥면)   ◄── up = −R_cam←imu · g_imu
 │                         d = p·forward                     ▲
 │                         l = p·right                       │
 │                                              │            │
 └─ IMU projected_gravity_b (N,3) ──────────────┴────────────┘
                lin_acc_b (N,3) ──┐
                                   │
   마스크: 0.03 < h < 0.40  그리고  |l| < 0.15  그리고  0.12 < d < 2.0
                                   │
   d_fused = min(d | 마스크)  (마스크 픽셀 25개 미만이면 inf)
                                   ▼
   판정  tilt > 25° → STOP_TILT │ |a| > 임계값 → STOP_IMPACT
         d_fused < 0.30 → DANGER │ < 0.60 → WARN │ else CLEAR
                                   ▼
   행동  DANGER/STOP 이면 **전진 명령의 +x 성분을 0 으로.** 후진·회전은 살린다.
```

보행은 이 파이프라인의 **입력을 만든다**:

```
  키보드 (carb)         삼각보행 생성기               IMU 가 읽는 것
  W/A/S/D/Q/E  ──►  (vx,vy,wz) ──► 발 궤적 ──► IK ──► 18개 다리 조인트
                         │                               │
                         └──► 몸통 끄덕임 ────────────────┘
```

### 4.4 핵심 코드

**(1) 뎁스를 점 집합으로 되돌린다**

```python
z = depth
x = (u - cx) / fx * z
y = (v - cy) / fy * z
points = torch.stack((x, y, z), dim=-1)      # (N,H,W,3) 카메라 광학 프레임
```

**(2) IMU 의 중력을 카메라 프레임으로 옮긴다 — 여기가 두 센서가 만나는 지점**

```python
g_cam = normalize(projected_gravity_b @ r_cam_imu.T)   # 카메라 프레임의 중력
up = -g_cam
ez = (0, 0, 1)                                          # 카메라 시선축
forward = normalize(ez - (ez·up) * up)                  # 시선에서 상방 성분을 뺀 것
right   = normalize(forward × up)
```

**(3) 중력 기준 높이로 바닥을 지운다**

```python
up_coord = (points * up).sum(-1)
ground   = nanquantile(up_coord[유효], 0.05)   # 보이는 점의 하위 5 백분위수 = 바닥면
height   = up_coord - ground

mask = finite & (height > 0.03) & (height < 0.40) \
     & (|dist_lat| < 0.15) & (0.12 < dist_fwd < 2.0)

d_fused = dist_fwd[mask].min()                 # 마스크 픽셀 25개 미만이면 inf
```

바닥면을 **상수가 아니라 추정값**으로 쓴 것이 핵심이다. 몸이 숙여지면 카메라가
실제로 낮아지는데, 설치 높이를 상수로 믿으면 모든 점의 높이가 그만큼 밀린다
(실험 조건 `pitch20_assumed` 가 그 실패를 보여준다).

**(4) 두 센서가 함께 최종 판정을 만든다**

```python
decision = CLEAR
decision = where(d_fused < 0.60, WARN,   decision)   # 뎁스 기여
decision = where(d_fused < 0.30, DANGER, decision)   # 뎁스 기여
decision = where(bump_acc > 임계값, STOP_IMPACT, decision)   # IMU 기여 (상위)
decision = where(tilt_deg > 25.0,  STOP_TILT,   decision)   # IMU 기여 (상위)
```

`d_fused` 자체가 이미 IMU 로 정렬된 좌표에서 나온 값이고, 그 위에 IMU 단독 조건이
덮어쓴다. **두 센서가 각각 다른 층위로 같은 판정 변수에 들어간다.**

### 5.1 조건 A — 걸어서 접근 (`walk`)

| t [s] | 참거리 [m] | d_fused [m] | 오차 | 판정 |

| 1.2 | 0.7784 | 0.7733 | +5.1 mm | CLEAR |
| 2.2 | 0.6950 | 0.6908 | +4.2 mm | CLEAR |
| 3.2 | 0.5959 | 0.5918 | +4.1 mm | WARN |
| 4.2 | 0.4800 | 0.4750 | +5.0 mm | WARN |

그 뒤 `cmd_vx` 가 0 으로 바뀌고 로봇은 제자리에 선다 — 판정이 숫자로 끝나지 않고
**행동으로 이어진 것이 로그에 그대로 남아 있다.**

**초기 수렴 구간**도 기록에 남아 있다. 장애물이 화면에 막 들어올 때는 마스크에 잡힌

| 0.35 | 0.847 | 1.066 | 장애물 윗부분이 들어오기 시작 |

| 0.55 이후 | — | — | 위 표의 ±5 mm 안으로 안정 |

### 5.5 조건 E — 바닥 추정을 끔 (`pitch20_assumed`) · 의도된 실패

`floor_mode` 를 `estimated` → `assumed_height` 로 바꿔, 설치 높이를 **상수로**
믿게 했다. 조건 D 와 나머지는 전부 같다.

| 장애물 거리 [m] | d_fused (추정) | d_fused (상수) | 장애물 픽셀 (추정 → 상수) |
|---|---|---|---|
| 0.90 | 0.870 | 0.870 | 1491 → 1142 |
| 0.70 | 0.659 | **inf** | 97 → **0** |
| 0.55 | 0.509 | 0.509 | 966 → **250** |
| 0.40 | 0.359 | 0.359 | 3052 → 2085 |
| 0.25 | 0.209 | 0.209 | 7900 → 6618 |

**0.70 m 조건에서 장애물을 통째로 놓쳤다** (픽셀 97 → 0, `d_fused` = `inf`).
다른 거리에서도 장애물 픽셀이 일관되게 줄어든다. 몸이 20도 숙으면 카메라가 실제로
약 6 cm 낮아지는데 상수를 믿으니 모든 점의 높이가 그만큼 밀려, 장애물 아랫부분이
높이 마스크 밖으로 빠져나간 것이다. **바닥을 추정해야 하는 이유**가 이 한 줄로
설명된다.

> **보행 조건에서는 이 차이가 거의 안 났다.** `walk` 와 `walk_assumed` 둘 다
> t=6.0 s / d_fused 0.2934 로 동일했다. 보행이 만드는 기울기가 **최대 2.92도**라
> 카메라 높이 변화가 작기 때문이다. **이 실패는 기울기가 클 때만 드러난다** —
> 조건을 정지 20도로 잡았기 때문에 보인 결과다.

### 5.6 조건 F — 계단 (`stairs`)

계단 4단(단 높이 5 cm, 깊이 14 cm). `d_fused` = 0.718 m, 융합 CLEAR(임계값 0.60 m
밖), 뎁스 단독 0.726 m CLEAR, **고정 ROI 는 `inf`** — 화면 위쪽만 보느라 **계단을
통째로 놓쳤다.** 5.7절에서 다시 나오는 false negative 다.

**이 조건은 융합이 무엇을 하는지 가장 직접적으로 보여준다.** 저장된 높이맵
(`stairs_d0.90.npz`)에서 장애물로 분류된 1751 픽셀의 높이 분포를 보면, **단별로
띠가 갈라진다**:

| 높이 구간 | 픽셀 수 |
|---|---|
| 0.00 ~ 0.06 m (1단) | 49 |
| 0.06 ~ 0.11 m (2단) | 820 |
| 0.11 ~ 0.16 m (3단) | 570 |
| 0.16 ~ 0.22 m (4단) | 312 |

전체 높이 범위는 0.060 ~ 0.200 m 로, 계단의 실제 높이(0.05 ~ 0.20 m)와 맞는다.
바닥(0 m 근처)은 **전부 제거됐다** — 마스크에 한 픽셀도 남지 않았다.

이 띠는 **IMU 없이는 만들 수 없다.** 뎁스만으로는 "앞에 뭔가 있다" 까지가 전부이고,
그것이 바닥인지 5 cm 단인지 20 cm 단인지 구분할 방법이 없다. 중력 방향을 알아야
각 점의 높이가 나오고, 그래야 "넘어갈 것 / 부딪칠 것" 을 가를 수 있다.

> 1단이 49 픽셀로 적은 이유는 단 높이 0.05 m 가 바닥 마스크 경계(0.03 m)에
> 가깝고, 2단에 가려 윗면이 거의 안 보이기 때문이다.

![계단 — 높이맵이 단별로 갈라진다](outputs/sensor_fusion/stairs_d0.90.png)

### 5.7 보조 실험 — 보행 중 전 구간 추적 (합성 뎁스)

Isaac 실행과 별개로, 동일한 융합 코드에 **합성 뎁스**를 넣어 1.10 m → 0.18 m 접근
전 구간(277 프레임)을 추적했다(`test_fusion.py` 조건 K). 몸통 끄덕임 ±3.5도.

| | 거리 오차(최대) | 임계값 0.30 m 에서 멈췄나 |
|---|---|---|
| **융합 (Depth + IMU)** | **1.4 cm** | **0.297 m — 3 mm 차이** |
| 고정 ROI | 85.2 cm | **못 멈춤** |
| 뎁스 단독 | 69.0 cm | 0.227 m — 7.3 cm 늦게 |

**고정 ROI 가 끝까지 못 멈춘 것**이 중요하다. 조건 D 에서는 바닥을 장애물로
**오인(false positive)** 했는데, 여기서는 **반대로 틀린다(false negative)**.
즉 임계값을 조정해서 고칠 수 있는 종류의 오류가 아니다.

## 6. 결과 분석

### 6.1 단일 센서와의 차이

| | 뎁스 단독 | 고정 ROI (뎁스만) | **융합 (Depth + IMU)** |
|---|---|---|---|
| 수평에서 거리 추정 | 바닥에 막혀 0.43 m 포화 | 정상 | 정상 (오차 3 mm) |
| 20도 숙였을 때 | 0.70 m 부터 DANGER 오경보 | 0.721 → 0.413 붕괴 | **유지** |
| 2 cm 턱 | WARN (멈춤) | CLEAR | **CLEAR (통과)** |
| 계단 | WARN | **inf — 놓침** | 0.718 m 로 포착 |
| 보행 중 추적 오차 | 69 cm | 85 cm | **1.4 cm** |

융합이 얻는 것은 셋이다.

1. **자세와 무관한 거리.** 바닥을 기하학적으로 제거하므로 카메라가 어디를 보든
   임계값을 다시 잡지 않아도 된다.
2. **물리적 의미를 갖는 임계값.** 거리 기준이 "사선 거리" 가 아니라 "중력 정렬
   수평거리" 라서 0.30 m 가 문자 그대로 "로봇 앞 30 cm" 다. 뎁스 단독이 7.3 cm
   늦게 멈추는 이유가 정확히 이것이다 — 최소 뎁스는 바닥까지의 사선 거리다.
3. **높이를 안다.** "멈출 것 / 넘어갈 것" 구분이 가능해진다. 거리만으로는 못 한다.

### 6.2 발생한 오류와 해결 과정

**(1) 단일 센서 기준선이 자기 그리퍼를 보고 있었다 — 비교 자체가 성립하지 않던 문제**

처음 Isaac 실행 로그(`run_log.csv`)에서 `d_naive` 가 이랬다:

| 장애물 참거리 | d_naive | 뎁스 단독 판정 |
|---|---|---|
| 0.90 m | **0.0642** | DANGER |
| 0.70 m | **0.0642** | DANGER |
| 0.55 m | **0.0642** | DANGER |
| 0.40 m | **0.0642** | DANGER |
| 0.25 m | **0.0642** | DANGER |

**장애물 거리와 무관하게 0.0642 m 로 고정.** 원인은 카메라 장착 위치였다. 카메라가
팔 끝에 달려 있고 시선축이 link4 의 +Z 인데 **그리퍼가 정확히 그 방향으로 뻗어
있어서, 화면 중앙 아래에 자기 손이 늘 찍힌다.** URDF 로 재 보면 카메라 기준
end_effector_link 가 전방 0.070 m 에 있다.

이 상태로 "융합이 단일 센서보다 낫다" 를 주장하면 안 된다. 그건 **"기준선이 애초에
고장" 이지 비교가 아니다.**

해결: **자기 몸 제거와 유효거리 창(0.12~2.0 m), 최소 픽셀 수를 기준선에도 똑같이
적용**했다. 근거는 자기 몸 마스킹이 융합의 기능이 아니라 **이 로봇에서 뎁스를
쓰려면 누구나 해야 하는 전처리**라는 것이다. 실기의 뎁스 단독 코드도 똑같이 한다.
그러고 나니 셋의 차이가 **중력 정렬과 높이 기반 바닥 제거 하나로 좁혀졌고**,
그제서야 비교가 성립했다. 5절의 모든 수치는 이 수정 이후의 값이다.

**(2) 조건별 CSV 를 덮어썼다**

`--tag` 를 바꾸지 않고 여러 조건을 돌려 앞 조건의 로그가 날아갔다. 조건마다
`{tag}_log.csv` 로 분리하고, 마지막에 `summary.csv` 로 묶는 단계를 스크립트에 넣었다.

**(3) 창을 닫으면 직접 조작한 세션의 로그가 통째로 사라졌다**

WASD 로 조작하다 창을 닫으면 PNG 는 남는데 CSV 가 안 생겼다. 루프를 빠져나온 뒤
마지막 프레임을 찍으려고 카메라를 한 번 더 읽는데, 창을 닫아 나온 경우 Isaac Sim 이
이미 내려가는 중이라 거기서 예외가 나고 **CSV 쓰는 코드에 도달하지 못했다.**
메모리에 있는 것(CSV)부터 쓰고, 시뮬레이터를 다시 건드리는 작업을 맨 뒤로 옮겼다.

**(4) 참거리 기록이 고정값이었다**

추정값과 맞대 볼 정답으로 `d_true` 를 기록했는데 316 행 내내 1.0313 m 였다.
`camera.data.pos_w` 로 카메라 월드 위치를 읽었더니 x 가 0 으로 들어왔다. 로봇
루트 포즈는 믿을 수 있으므로 `root_pos_w` + 자세로 돌린 상수 오프셋으로 카메라
위치를 만들도록 고쳤다. 5.1 절의 "참거리" 열이 그 수정 이후 값이다.

**(5) 보행 중에는 충격 판정이 계속 걸렸다**

발이 땅에 닿을 때마다 가속도가 튀어서, 정지 기준으로 잡은 6 m/s² 으로는 보행 내내
`STOP_IMPACT` 였다. 지금은 보행 모드에서 임계값을 25 m/s² 으로 올려 피했는데,
**이건 해결이 아니라 회피다.** 아래 개선 방향에 적었다.

**(6) URDF 자체의 불일치 — RM 다리**

보행 기구학을 URDF 와 대조하는 테스트가 RM 다리에서만 17 mm 오차를 냈다. 확인해
보니 `end_RM_joint` 의 origin 이 나머지 다섯 다리와 어긋나 있어 발끝 횡 오프셋이
−17.4 mm(다른 다리는 ±1.5~3 mm), 링크 길이도 0.1113 m(다른 다리 0.1156 m)였다.
Hiwonder URDF 쪽 불일치로 보인다. 상수를 다리마다 따로 뽑도록 해 그대로 맞춰
넣었고, 오차는 0.21 mm 로 줄었다.

### 6.3 한계

1. **사각지대.** 장착 기하 때문에 카메라 앞 약 0.29 m 안쪽 바닥이 보이지 않는다.
   그보다 가까운 낮은 장애물은 **원리적으로** 못 본다.
2. **바닥 추정이 바닥을 봐야 작동한다.** 하위 5 백분위수를 바닥으로 보므로,
   벽에 바짝 붙어 서면 그 백분위수가 벽이 되어 전체 높이가 밀린다.
3. **단일 평면 가정.** 계단이나 경사 바닥에서는 "바닥 한 장" 가정이 깨진다.
4. **측정 시점을 0 으로 맞춘 것은 시뮬레이터라 가능한 일이다.** 실기는 IMU 수백 Hz,
   뎁스 30 Hz 라 몸이 빠르게 끄덕이면 뎁스 한 장 안에서 자세가 변해 롤링 왜곡이 생긴다.
5. **IMU 가 이상적이다.** Isaac 의 `Imu` 는 바이어스·노이즈가 없다. 실기 저장소의
   `imu_calib.yaml` 에는 축별 바이어스 (0.3166, 0.4634, 0.6945) 와 최대 0.05 rad
   (약 3도)의 축 비정렬이 들어 있다. **시뮬 결과가 실기보다 좋게 나오는 가장 큰 이유다.**
6. **보행 중 충격 판정이 사실상 못 쓴다.** 6.2-(5) 의 임계값 상향은 회피책이다.
7. **보행이 운동학 모드다.** 이번 실험은 `--walk_mode kinematic` 으로 돌렸다.
   다리는 보행 궤적대로 움직이지만 몸통은 명령 속도를 적분해 직접 옮기므로
   **접지 물리가 아니고, 몸통 끄덕임(최대 2.92도)도 보행 위상에 물려 넣은 합성
   모델이다.** 측정된 보행 끄덕임이 아니다. 물리 접지 보행(`--walk_mode physics`)은
   PD 게인이 미검증이라 이번 제출에서는 돌리지 않았다.

### 6.4 개선 방향

- **충격 판정에 저역통과 또는 보행 위상 게이팅.** 보행 발소리는 보행 주파수
  (약 0.83 Hz)와 그 배음에 몰려 있고 충돌은 광대역이다. 보행 위상을 이미 알고
  있으므로 **착지 구간에만 임계값을 올리는** 게이팅이 더 간단하다. 한계 6번의 정면 해법.
- **물리 접지 보행으로 재실험.** PD 게인을 맞춰 `--walk_mode physics` 로 걷게 한 뒤
  IMU 의 실제 끄덕임을 재서, 이번에 쓴 합성 모델(±3.5도)이 얼마나 맞는지 대조한다.
  한계 7번의 해법.
- **IMU 에 실측 바이어스·축 비정렬을 주입하고 상보 필터/EKF 를 붙인다.**
  `imu_calib.yaml` 의 값을 그대로 쓰면 된다. 한계 5번의 해법.
- **바닥을 백분위수 대신 RANSAC 평면 적합으로 추정.** 경사 바닥과 계단에 대응
  가능해진다. 한계 2·3번의 해법.
- **중력 정렬 좌표에서 2.5D 높이맵으로 누적.** 단일 프레임 노이즈에 덜 흔들리고,
  발 디딜 곳 판단까지 확장된다.
- **LiDAR 를 더해 3센서로.** RosPider 는 `lidar_link` 도 URDF 에 갖고 있다
  (base_link 기준 (0.10163, 0.00022, 0.03515) m). `RayCaster` 로 붙일 수 있다.
