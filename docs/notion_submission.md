## 2. 과제 목표

### 2.1 해결하려는 상황

사용자가 RosPider 를 **WASD 키보드로 원격 조종**하여 실내를 보행시키는 상황을
가정하였습니다. 조종자는 로봇에 장착된 카메라 영상만을 확인할 수 있으며 로봇의
발밑은 관찰할 수 없습니다. 이 조건에서 로봇은 조종자가 전진 명령을 내리더라도
**충돌이 예상되는 물체 앞에서는 스스로 정지해야** 합니다. 동시에 **넘어갈 수 있는
2 cm 높이의 턱 앞에서는 정지해서는 안 됩니다.** 그러한 지형마다 정지할 경우 원격
조종 자체가 불가능해지기 때문입니다.

따라서 로봇이 매 순간 판단해야 하는 질문은 다음 하나로 정리됩니다.

> **지금 전진해도 되는가?**

이 판단은 양쪽 방향 모두로 실패할 수 있으며, 어느 쪽도 허용되지 않습니다. 정지하지
못하면 충돌하고, 불필요하게 정지하면 조종할 수 없습니다. 그러므로 본 과제는
"장애물의 유무"를 판별하는 문제가 아니라 **"넘어갈 수 있는 지형과 충돌 대상을
구분"하는 문제**로 정의됩니다.

### 2.2 센서 융합이 필요한 이유

**뎁스 카메라만으로는 이 판단이 불가능합니다.** RosPider 의 뎁스 카메라는 몸통이
아니라 **팔 끝(link4)** 에 장착되어 있으며, 관측 자세에서 전방을 **24.2도 아래로**
향합니다(URDF 체인에서 계산한 값입니다). 따라서 화면 아래쪽은 **항상 바닥**이며,
"가장 가까운 뎁스 값"으로 장애물을 탐색하면 바닥이 먼저 검출됩니다.

이에 대한 일반적인 대응은 화면 위쪽 영역만 사용하는 방식입니다(고정 ROI). 로봇을
정지시킨 상태에서는 이 방식이 정상적으로 동작합니다. 그러나 **보행을 시작하면
성립하지 않습니다.** 6족 보행은 세 다리씩 교대로 지면을 딛기 때문에 지지 다각형이
매 반주기마다 변하고, 몸통이 보행 주기에 맞추어 지속적으로 기울어집니다. 몸체가
숙여지면 잘라낸 영역 안으로 바닥이 포함됩니다. **화면의 어느 영역이 바닥인지가 매
프레임 변하므로, 화면 좌표에 고정된 규칙은 원리적으로 성립할 수 없습니다.**

**IMU 가 이 문제를 해결합니다.** IMU 는 거리를 측정하지 못하지만 **중력 방향**을
제공합니다. 중력 방향을 알면 뎁스로 복원한 각 점에 대해 "바닥으로부터의 높이"를
계산할 수 있고, 바닥을 화면 좌표가 아니라 **기하학적으로** 제거할 수 있습니다.
또한 높이를 알 수 있으므로 2.1 의 요구사항이 직접 해결됩니다. **높이 3 cm 이하의
지형은 통과 가능한 것으로 판단하여 장애물로 계수하지 않습니다.**

### 2.3 센서 선택과 역할

| 센서 | 출력 | 역할 | 부재 시 문제 |
|---|---|---|---|
| Depth | `distance_to_image_plane` | 전방 물체까지의 **거리**와 형상 | 근접 정도를 측정할 수 없습니다 |
| IMU | `projected_gravity_b` | 몸체 **자세**(중력 방향) | 뎁스의 어느 점이 바닥인지 알 수 없습니다 |
| IMU | `lin_acc_b` | **충격** | 이미 충돌했는지를 카메라로는 확인할 수 없습니다 |

두 센서는 각각의 화면을 나란히 제시하는 수준에 그치지 않고 **하나의 판정 변수로
결합됩니다.** IMU 가 뎁스 점군의 좌표계를 중력 방향에 정렬시키고, **정렬된 좌표에서만
거리 판정이 수행됩니다.** 둘 중 하나를 제거하면 처리 과정이 성립하지 않습니다.

**IMU 설정**

`gravity_bias` 를 `(0, 0, 0)` 으로 설정하였습니다. 기본값인 `(0, 0, 9.81)` 은 실제
IMU 와 동일하게 정지 상태에서도 +9.81 이 측정되도록 만들며, 이 경우 충격 임계값을
"9.81 로부터의 편차"로 정의해야 하므로 처리가 복잡해집니다. 0 으로 설정하면
`lin_acc_b` 가 **순수 운동가속도**가 되어 `|a| > 임계값` 이라는 단순한 조건을 바로
적용할 수 있습니다. 자세(기울기)는 `projected_gravity_b` 로부터 얻으며, 이 값은
`gravity_bias` 설정과 무관합니다.

## 4. 구현 방법

### 4.1 데이터 수집 과정

시뮬레이션은 매 물리 스텝(120 Hz)마다 진행되며, **6 스텝마다(20 Hz) 판정**을
수행합니다. 실기 뎁스 카메라의 동작 주파수인 30 Hz 와 같은 자릿수로 설정한 것입니다.

```python
depth      = scene["camera"].data.output["distance_to_image_plane"]  # (N,H,W) [m]
intrinsics = scene["camera"].data.intrinsic_matrices                 # (N,3,3)
imu        = scene["imu"].data                                       # projected_gravity_b, lin_acc_b
```

**외부 파라미터는 매 스텝 재계산합니다.** 카메라가 팔 끝에 장착되어 있어 팔이
움직이면 `R_cam←imu` 가 변하기 때문입니다. joint3 을 0.4 rad 만 움직여도 행렬 성분이
0.385 변화합니다.

```python
q = ext.arm_joint_dict(joint_names, robot.data.joint_pos[0].cpu().numpy())
r_cam_imu = ext.r_cam_imu(q)   # URDF 체인을 런타임에 전개
```

> 이 방식이 타당한 이유는 **실기에서도 동일한 절차를 사용하기 때문입니다.** 팔
> 조인트 각도는 서보 엔코더(`joint_states`)로 측정할 수 있으며, URDF 로 tf 를
> 계산하여 카메라 자세를 얻습니다. 본 구현에서 읽는 `robot.data.joint_pos` 가 그
> 엔코더에 해당합니다. 시뮬레이터가 보유한 정답 포즈를 직접 사용하지 않았습니다.
> 정답 포즈를 사용하면 IMU 가 불필요해지므로 과제의 전제가 성립하지 않습니다.

### 4.2 단위·좌표계·측정 시점

| 항목 | 값 |
|---|---|
| 뎁스 | `distance_to_image_plane`, 단위 **m**, 카메라 광학 **z축** 기준 |
| 측정 실패 픽셀 | `inf` (`isfinite` 로 제거) |
| 카메라 광학 프레임 | ROS 규약. **+X 오른쪽, +Y 아래, +Z 시선** |
| IMU 프레임 | `imu_link`. base_link 대비 **yaw −90도** |
| 중력 | 단위벡터(크기 1) |
| 가속도 | m/s² (중력 성분을 제외한 운동가속도) |
| 각도 | 내부 계산은 rad, 출력은 deg |
| 로봇 몸 좌표 | base_link. +X 전방, +Y 좌측, +Z 상방 |
| **측정 시점** | 두 센서 모두 `update_period=0`. **동일한 물리 스텝에서 읽으므로 시점 차이가 0 입니다** |

> 측정 시점을 0 으로 맞출 수 있는 것은 시뮬레이터이기 때문입니다. **실기에서는
> IMU 가 수백 Hz, 뎁스가 30 Hz** 로 동작하므로, 몸체가 빠르게 기울어지는 구간에서는
> 뎁스 한 프레임 내에서 자세가 변하여 롤링 왜곡이 발생합니다. 6.3 한계 항목에
> 기술하였습니다.

### 4.3 융합 흐름도

```
 ┌─ 뎁스 (N,H,W) [m] ──► 역투영 ──► 점 집합 p (카메라 광학 프레임)
 │        intrinsics K          x=(u-cx)/fx·z, y=(v-cy)/fy·z, z=depth
 │                                              │
 │                                              ▼
 │                         h = p·up − (바닥면)   ◄── up = −R_cam←imu · g_imu
 │                         d = p·forward                     ▲
 │                         l = p·right                       │
 │                                              │            │
 └─ IMU projected_gravity_b (N,3) ──────────────┴────────────┘
                lin_acc_b (N,3) ──┐
                                   │
   마스크: 0.03 < h < 0.40  그리고  |l| < 0.15  그리고  0.12 < d < 2.0
                                   │
   d_fused = min(d | 마스크)  (마스크 픽셀 25개 미만이면 inf)
                                   ▼
   판정  tilt > 25° → STOP_TILT │ |a| > 임계값 → STOP_IMPACT
         d_fused < 0.30 → DANGER │ < 0.60 → WARN │ else CLEAR
                                   ▼
   행동  DANGER/STOP 이면 전진 명령의 +x 성분을 0 으로 설정. 후진·회전은 유지.
```

보행은 이 처리 과정의 **입력을 생성합니다.**

```
  키보드 (carb)         삼각보행 생성기               IMU 가 측정하는 것
  W/A/S/D/Q/E  ──►  (vx,vy,wz) ──► 발 궤적 ──► IK ──► 18개 다리 조인트
                         │                               │
                         └──► 몸통 기울어짐 ──────────────┘
```

### 4.4 핵심 코드

**(1) 뎁스를 점 집합으로 역투영합니다**

```python
z = depth
x = (u - cx) / fx * z
y = (v - cy) / fy * z
points = torch.stack((x, y, z), dim=-1)      # (N,H,W,3) 카메라 광학 프레임
```

**(2) IMU 의 중력을 카메라 프레임으로 변환합니다 — 두 센서가 결합되는 지점입니다**

```python
g_cam = normalize(projected_gravity_b @ r_cam_imu.T)   # 카메라 프레임의 중력
up = -g_cam
ez = (0, 0, 1)                                          # 카메라 시선축
forward = normalize(ez - (ez·up) * up)                  # 시선에서 상방 성분을 제거
right   = normalize(forward × up)
```

**(3) 중력 기준 높이로 바닥을 제거합니다**

```python
up_coord = (points * up).sum(-1)
ground   = nanquantile(up_coord[유효], 0.05)   # 관측된 점의 하위 5 백분위수를 바닥면으로
height   = up_coord - ground

mask = finite & (height > 0.03) & (height < 0.40) \
     & (|dist_lat| < 0.15) & (0.12 < dist_fwd < 2.0)

d_fused = dist_fwd[mask].min()                 # 마스크 픽셀 25개 미만이면 inf
```

바닥면을 **상수가 아니라 추정값**으로 사용한 점이 핵심입니다. 몸체가 숙여지면
카메라의 실제 높이가 낮아지는데, 설치 높이를 상수로 가정하면 모든 점의 높이가 그만큼
편향됩니다. 실험 조건 `pitch20_assumed` 가 이 실패를 보여줍니다.

**(4) 두 센서가 함께 최종 판정을 구성합니다**

```python
decision = CLEAR
decision = where(d_fused < 0.60, WARN,   decision)   # 뎁스 기여
decision = where(d_fused < 0.30, DANGER, decision)   # 뎁스 기여
decision = where(bump_acc > 임계값, STOP_IMPACT, decision)   # IMU 기여 (상위)
decision = where(tilt_deg > 25.0,  STOP_TILT,   decision)   # IMU 기여 (상위)
```

`d_fused` 자체가 이미 IMU 로 정렬된 좌표에서 산출된 값이며, 그 위에 IMU 단독 조건이
상위 조건으로 적용됩니다. **두 센서가 서로 다른 층위에서 동일한 판정 변수에
기여합니다.**

측정하면 카메라 기준 end_effector_link 가 전방 0.070 m 에 위치합니다.

이 상태에서는 융합이 단일 센서보다 우수하다는 결론을 도출할 수 없습니다. 비교
대상인 기준선 자체가 정상 동작하지 않는 상태이기 때문입니다.

해결 방법으로 **자체 신체 제거와 유효거리 창(0.12~2.0 m), 최소 픽셀 수 조건을
기준선에도 동일하게 적용**하였습니다. 근거는 자체 신체 마스킹이 융합의 고유 기능이
아니라 **이 로봇에서 뎁스를 사용하기 위해 필수적인 전처리**라는 점이며, 실기의 뎁스
단독 코드에서도 동일한 처리를 수행합니다. 이 수정 이후 세 방식의 차이는 **중력
정렬과 높이 기반 바닥 제거 한 가지로 좁혀졌고**, 비교가 성립하게 되었습니다. 5절의
모든 수치는 이 수정 이후의 값입니다.

**(2) 조건별 CSV 가 덮어써진 문제**

`--tag` 를 변경하지 않은 채 여러 조건을 실행하여 이전 조건의 로그가 소실되었습니다.
조건마다 `{tag}_log.csv` 로 분리하고, 마지막에 `summary.csv` 로 통합하는 단계를
스크립트에 추가하였습니다.

**(3) 창을 닫으면 직접 조작한 세션의 로그가 소실되던 문제**

WASD 로 조작한 뒤 창을 닫으면 PNG 는 저장되었으나 CSV 가 생성되지 않았습니다.
루프 종료 후 마지막 프레임을 저장하기 위해 카메라를 한 번 더 읽는데, 창을 닫아
루프가 종료된 경우에는 Isaac Sim 이 이미 종료 중이므로 해당 지점에서 예외가 발생하고
**CSV 저장 코드에 도달하지 못하였습니다.** 메모리에 보관된 데이터(CSV)를 먼저
저장하고, 시뮬레이터에 다시 접근하는 작업을 마지막으로 이동시켰습니다.

**(4) 참거리 기록이 고정값이던 문제**

추정값과 비교할 기준값으로 `d_true` 를 기록하였으나 316 행 전체에서 1.0313 m 로
동일하였습니다. `camera.data.pos_w` 로 카메라의 월드 위치를 읽었을 때 x 성분이 0 으로
전달되었기 때문입니다. 로봇 루트 포즈는 신뢰할 수 있으므로 `root_pos_w` 와 자세로
회전시킨 상수 오프셋을 사용하여 카메라 위치를 계산하도록 수정하였습니다. 5.1 의
참거리 열은 이 수정 이후의 값입니다.

**(5) 보행 중 충격 판정이 지속적으로 발생한 문제**

발이 지면에 접촉할 때마다 가속도가 상승하여, 정지 상태 기준으로 설정한 6 m/s² 에서는
보행 전 구간에서 `STOP_IMPACT` 가 발생하였습니다. 현재는 보행 모드에서 임계값을
25 m/s² 으로 상향하여 회피하였으나, **근본적인 해결이 아니라 회피책입니다.** 6.4 에
개선 방향을 기술하였습니다.

**(6) URDF 자체의 불일치 — RM 다리**

보행 기구학을 URDF 와 대조하는 테스트에서 RM 다리에서만 17 mm 오차가 발생하였습니다.
확인 결과 `end_RM_joint` 의 origin 이 나머지 다섯 다리와 상이하여 발끝 횡 오프셋이
−17.4 mm(다른 다리는 ±1.5~3 mm)였고, 링크 길이도 0.1113 m(다른 다리 0.1156 m)로
달랐습니다. Hiwonder URDF 측의 불일치로 판단됩니다. 상수를 다리마다 개별적으로
산출하도록 수정하여 반영하였으며, 오차는 0.21 mm 로 감소하였습니다.

### 6.3 한계

1. **사각지대.** 장착 기하 구조로 인해 카메라 전방 약 0.29 m 이내의 바닥은 관측되지
   않습니다. 그보다 가까운 낮은 장애물은 **원리적으로** 검출할 수 없습니다.
2. **바닥 추정은 바닥이 관측되어야 동작합니다.** 하위 5 백분위수를 바닥으로
   간주하므로, 벽에 근접하여 정지한 경우 해당 백분위수가 벽이 되어 전체 높이가
   편향됩니다.
3. **단일 평면 가정.** 계단이나 경사 바닥에서는 바닥이 하나의 평면이라는 가정이
   성립하지 않습니다.
4. **측정 시점을 0 으로 맞출 수 있는 것은 시뮬레이터이기 때문입니다.** 실기는 IMU
   수백 Hz, 뎁스 30 Hz 로 동작하므로 몸체가 빠르게 기울어지면 뎁스 한 프레임 내에서
   자세가 변하여 롤링 왜곡이 발생합니다.
5. **IMU 가 이상적인 센서입니다.** Isaac Sim 의 `Imu` 는 바이어스와 노이즈가
   없습니다. 실기 저장소의 `imu_calib.yaml` 에는 축별 바이어스
   (0.3166, 0.4634, 0.6945)와 최대 0.05 rad(약 3도)의 축 비정렬이 기록되어 있습니다.
   **시뮬레이션 결과가 실기보다 우수하게 나오는 가장 큰 원인입니다.**
6. **보행 중에는 충격 판정을 사실상 사용할 수 없습니다.** 6.2-(5) 의 임계값 상향은
   회피책에 해당합니다.
7. **보행이 운동학 모드로 수행되었습니다.** 본 실험은 `--walk_mode kinematic` 으로
   실행하였습니다. 다리는 보행 궤적에 따라 움직이지만 몸통은 명령 속도를 적분하여
   직접 이동시키므로 **접지 물리가 반영되지 않았으며, 몸통 기울어짐(최대 2.92도)도
   보행 위상에 연동시킨 합성 모델입니다.** 측정된 보행 기울어짐이 아닙니다. 물리
   접지 보행(`--walk_mode physics`)은 PD 게인이 검증되지 않아 이번 제출에서는
   실행하지 않았습니다.

### 6.4 개선 방향

- **충격 판정에 저역통과 필터 또는 보행 위상 게이팅 적용.** 보행 시 발생하는 진동은
  보행 주파수(약 0.83 Hz)와 그 배음에 집중되는 반면 충돌은 광대역 특성을 갖습니다.
  보행 위상을 이미 알고 있으므로 **착지 구간에만 임계값을 상향하는** 게이팅이 더
  간단한 방법입니다. 한계 6번에 대한 직접적인 해결책입니다.
- **물리 접지 보행으로 재실험.** PD 게인을 조정하여 `--walk_mode physics` 로 보행
  시킨 뒤 IMU 의 실제 기울어짐을 측정하고, 이번에 사용한 합성 모델(±3.5도)과
  대조합니다. 한계 7번에 대한 해결책입니다.
- **IMU 에 실측 바이어스와 축 비정렬을 주입하고 상보 필터 또는 EKF 를 적용.**
  `imu_calib.yaml` 의 값을 그대로 사용할 수 있습니다. 한계 5번에 대한 해결책입니다.
- **바닥면을 백분위수 대신 RANSAC 평면 적합으로 추정.** 경사 바닥과 계단에 대응할
  수 있게 됩니다. 한계 2번과 3번에 대한 해결책입니다.
- **중력 정렬 좌표에서 2.5D 높이맵으로 누적.** 단일 프레임의 노이즈에 덜 민감해지며,
  디딤 위치 판단까지 확장할 수 있습니다.
- **LiDAR 를 추가하여 3센서 구성.** RosPider 는 `lidar_link` 도 URDF 에 보유하고
  있습니다(base_link 기준 (0.10163, 0.00022, 0.03515) m). `RayCaster` 로 구현
  가능합니다.
