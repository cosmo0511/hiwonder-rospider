# 실물 ROSpider 측정 기록

실물에서 잰 값을 시뮬 학습에 넣기 위한 기록이다. 항목마다 왜 재는지, 어떻게 쟀는지, 결과, 시뮬과 다른 점을 적는다.

## 연결 (2026-11-11)

- 노트북 ↔ 로봇 Jetson: USB-C 케이블. 로봇 `192.168.55.1`, 노트북 `192.168.55.100`. 와이파이(eduroam)는 그대로 쓴다.
  Jetson이 USB 랜카드를 두 개 만드는데 하나만 IP를 받는다. 다른 하나의 "연결 실패" 알림은 무시해도 된다.
- 로그인: `ssh ubuntu@192.168.55.1` (노트북 SSH 키 등록함). 로봇 셸은 zsh라서 ROS는 `bash -c "source /opt/ros/humble/setup.bash; source ~/ros2_ws/install/setup.bash; export ROS_DOMAIN_ID=10; ..."`로 쓴다.
- 로봇 시계가 2026-03-05 20:02(중국 시간)로 부팅마다 돌아간다. 로그 시간은 믿지 말 것.
- 측정 전에 `~/.stop_ros.sh`로 자동 실행(앱, 음성, self_balancing 등)을 끄고 서보 보드 노드만 켠다. 다른 노드가 서보에 명령을 보내면 측정이 틀어진다.
  ```bash
  ros2 launch ros_robot_controller ros_robot_controller.launch.py
  ```
  원래대로 돌리려면 로봇을 재부팅한다 (부팅 때 팔·다리가 시작 자세로 움직이니 바닥에 두고).

## 로봇 드라이버 정리

| 할 일 | 방법 |
|---|---|
| 서보 목표 보내기 | 토픽 `/ros_robot_controller/bus_servo/set_position` (`ros_robot_controller_msgs/ServosPosition`: duration [s], id, position 0 ~ 1000) |
| 서보 위치 읽기 | 서비스 `/ros_robot_controller/bus_servo/get_state` (`get_position: 1`). 실제 서보를 읽는 건 이것뿐 |
| 쓰면 안 되는 것 | `/controller_manager/servo_states`, `/joint_states`: 보낸 명령값을 돌려줄 뿐 실제 위치가 아니다 (로봇의 `rl_walk.py` 주석) |
| 펄스 → 각도 | 1000 펄스 = 240°, 500이 0. `servo_controller.yaml`에서 min > max인 관절은 뒤집힘: `rad = (500 - p)·0.0041888`, 아니면 `(p - 500)·0.0041888` (드라이버 `joint_position_controller.py`와 같은 식) |
| IMU | `/ros_robot_controller/imu_raw` (가속도, 자이로. 자세 쿼터니언은 imu_filter가 켜져 있을 때만) |
| 배터리 | `/ros_robot_controller/battery` (mV) |
| 서보 ID | 다리: tibla 1·2 / 7·8 / 13·14, femur 3·4 / 9·10 / 15·16, coxa 5·6 / 11·12 / 17·18 (왼쪽·오른쪽, 앞·가운데·뒤). 팔·그리퍼 19 ~ 24 |

**드라이버 버그:** `get_state`에 `get_voltage` 또는 `get_torque_state`를 넣으면 서보 보드 노드가 죽는다 (없는 함수 `bus_servo_read_voltage`, `bus_servo_read_torque`를 부름). 노드가 죽으면 서보 읽기가 전부 막히니 쓰지 말 것.
처음 접속했을 때 이 노드가 이미 죽어 있었는데 원인은 확인 못 했다 (같은 시각에 보드 USB가 다시 잡힘).

## 1. 읽기만 하는 측정 (로봇 안 움직임)

스크립트: `real/measure_passive.py` (로봇 `/tmp`에 복사해서 실행). 결과 원본: `real/measure_passive_20261111.json`.
로봇은 부팅 후 시작 자세로 선 상태, 측정 중 아무 명령도 보내지 않았다.

### 서보 읽기 시간 → 정책 제어 주기

**왜:** 정책은 매 스텝 관절 위치를 읽어야 한다. 18개를 읽는 시간이 곧 제어 주기의 한계다. 3-p를 18 Hz로 학습한 근거를 직접 확인한다.

| 한 번에 읽는 서보 수 | 평균 | 95 % | 주기 |
|---|---|---|---|
| 18 | 50.5 ms | 54.4 ms | 19.8 Hz |
| 6 | 18.2 ms | 19.9 ms | 55 Hz |
| 1 | 4.7 ms | 6.2 ms | 211 Hz |

- 서보 하나에 약 2.8 ms. 18개 전부 읽으면 약 20 Hz가 한계다. 3-p(18.2 Hz)가 맞다. 50회 중 실패 0.
- 읽기와 쓰기가 같은 버스를 쓰므로, 실제 루프는 쓰기 시간까지 더해 더 느려질 수 있다 (아직 안 잼).

### 서보 상태 (선 자세에서)

**왜:** 오프셋은 서보에 저장된 0점 보정값이다. 온도가 높으면 서보 힘이 약해지고 보호 기능으로 꺼질 수 있다.

| 관절 | LF | LM | LR | RF | RM | RR |
|---|---|---|---|---|---|---|
| coxa 위치 (rad) | 0.117 | 0.013 | -0.113 | -0.113 | 0.000 | 0.113 |
| femur 위치 (rad) | 0.787 | 0.779 | 0.767 | 0.758 | 0.779 | 0.783 |
| tibla 위치 (rad) | -0.959 | -0.712 | -0.653 | -0.649 | -0.716 | -0.658 |
| coxa 오프셋 (펄스) / 온도 (°C) | -5 / 55 | 2 / 64 | -14 / 39 | 3 / 37 | -8 / 38 | -6 / 62 |
| femur 오프셋 / 온도 | -2 / 71 | 12 / 65 | -5 / 37 | -5 / 47 | -6 / 67 | -5 / 68 |
| tibla 오프셋 / 온도 | -11 / 52 | -18 / 70 | -6 / 37 | 12 / 36 | 10 / 72 | -12 / 38 |

- 오프셋은 ±18 펄스(±4°) 이내.
- **온도:** 서 있기만 해도 여러 서보가 62 ~ 72 °C다. 측정 사이사이에 로봇을 내려놓고 식힐 것.
- **배터리:** 11.95 V (3셀).

### 실물 선 자세 vs 시뮬 기본자세 (중요)

**왜:** 정책의 관절 관측은 "기본자세와의 차이"고, CPG 걸음도 기본자세를 기준으로 다리를 움직인다. 실물의 기본자세가 시뮬과 다르면 정책이 처음 보는 입력을 받는다.

| | coxa (앞 / 가운데 / 뒤) | femur | tibla |
|---|---|---|---|
| 실물 시작 자세 (부팅 후) | ±0.11 / 0.0 / ∓0.11 | +0.77 | -0.65 ~ -0.72 (LF만 -0.96) |
| 시뮬 기본자세 (`robot_cfg.stand_pose`) | ±0.01 ~ 0.02 (RM만 0.14) | +0.04 ~ +0.10 | -0.07 ~ -0.12 |

- femur가 약 0.7 rad, tibla가 약 0.55 rad 다르다. 시뮬 로봇은 다리를 거의 편 자세로 서고, 실물은 무릎을 굽히고 낮게 선다.
- 펄스 → 각도 부호는 드라이버 식을 그대로 썼다. 로봇을 움직여서 부호가 URDF와 같은지 확인하는 건 아직 안 했다.
- 시뮬 coxa_RM 0.14는 URDF의 RM 오프셋 때문이다. 실물은 0이다. 로봇의 `rl_walk.py`도 coxa_RM 부호가 어긋난다고 적어 두었다.
- **결론(예정):** 확인이 끝나면 실물 시작 자세를 기본자세로 바꾸고 다시 학습해야 한다.

### IMU (가만히 선 상태 5초)

**왜:** 정책은 몸 기울기(중력 방향)와 회전 속도를 본다. 잡음과 치우침(bias)을 알아야 학습 때 같은 크기의 잡음을 넣을 수 있다. 방향 오차 관측은 자이로 z를 적분하므로 z 치우침이 쌓인다.

| | x | y | z |
|---|---|---|---|
| 가속도 평균 (m/s²) | -0.001 | 0.839 | 9.806 |
| 가속도 잡음 (표준편차) | 0.002 | 0.002 | 0.002 |
| 자이로 평균 (rad/s) | 0.0106 | 0.0113 | -0.0014 |
| 자이로 잡음 | 0.0008 | 0.0008 | 0.0009 |

- 주기 48.8 Hz.
- 가속도 y 0.84 → 몸(또는 IMU)이 약 4.9° 기울어 있다. LF tibla만 -0.96인 것과 관계 있을 수 있다 (미확인).
- 자이로 z 치우침 -0.0014 rad/s → 방향 오차가 1분에 약 0.08 rad(5°) 쌓인다. 실물에서는 시작 때 치우침을 빼 주면 된다.
- 걸을 때의 잡음은 따로 재야 한다.

## 2. 관절 방향 확인 (2026-11-11, 바닥에 선 채로)

원본 로그: `logs/20261111_floor_check.txt`. 스크립트: `floor_check.py`(센서로 판단), `leg_lift.py`(다리 하나 들고 사람이 봄), `sign_check.py`(읽기).
로봇은 갓 부팅해 시작 자세로 선 상태. 움직임은 0.1 rad(약 6°)을 1초에 걸쳐 주고 바로 되돌렸다.

**왜:** 실물 시작 자세와 정책 출력을 시뮬로 옮기려면 각도의 + 방향이 드라이버(서보 → rad)와 URDF에서 같아야 한다.

### 시작 자세 (갓 부팅, 좌우 거의 대칭) → 재학습 기본자세 후보

| | coxa | femur | tibla |
|---|---|---|---|
| 드라이버 각도 (rad) | -0.013 ~ +0.017 | +0.867 ~ +0.888 | -0.804 ~ -0.829 |
| 펄스 (왼쪽 / 오른쪽) | 약 500 / 500 | 288 ~ 292 / 707 ~ 712 | 694 ~ 698 / 306 ~ 308 |

- 1절의 값(femur 0.77)은 20분 넘게 서 있어 처진 뒤의 값이었다. 기본자세로는 이 값을 쓴다.
- coxa_RM은 아래처럼 부호를 뒤집어야 하지만 값이 0 근처라 기본자세에는 영향이 거의 없다.
- 팔 (펄스): 19: 502, 20: 718, 21: 128, 22: 149, 23: 500, 24: 500. 설정 파일 `init_pose.yaml`(500, 650, 40, 215, 500, 500)과 20 ~ 22번이 70 ~ 90 펄스 다르다 (무게로 처진 것으로 보임). 시뮬 팔 자세는 실제 값에 맞출 것. 팔 관절 펄스 → rad 변환은 아직 안 함.

### 방향 판정

| 관절 | 방법 | 결과 | URDF 예상 | 판정 |
|---|---|---|---|---|
| femur | 6개 같이 +0.1, 손목 뎁스로 앞쪽 책상 면까지 거리 | 590 → 581 mm (몸이 9 mm 내려감) | 발 들림 → 몸 내려감, 약 9 mm | 같음 |
| femur | 왼쪽 3개만 +0.1, IMU 가속도 | x +0.25 m/s² (왼쪽으로 기욺) | 왼쪽 내려감 | 같음. **IMU x = 로봇 옆 방향** |
| tibla | 6개 같이 / 왼쪽만 +0.1 | 몸 높이 -1 mm, 기울기 0.01 | 변화 아주 작음 | 이 방법으로는 판정 불가 |
| tibla | LM을 femur +0.3으로 들고 tibla +0.2, 사람이 봄 | 발끝이 몸 바깥쪽 | 바깥쪽 | 같음 |
| coxa | 6개 같이 +0.1, 자이로 z 적분 | -0.048 rad (위에서 시계 방향) | 왼발 뒤 · 오른발 앞 → 몸 시계 방향 | 같음 |
| coxa | LM만 +0.1 | z -0.004 | 시계 방향 | 같음 |
| **coxa_RM** | RM만 +0.1 | z **+0.009** | 시계 방향 | **반대** |
| **coxa_RM** | RM을 들고 coxa +0.4, 사람이 봄 | 발이 **뒤쪽** | 앞쪽 | **반대 (확정)** |

- **coxa_RM만 부호가 반대다.** URDF의 오른쪽 coxa 세 개는 축이 같다(z, +). 그런데 서보 설정 파일에서 coxa_RF와 coxa_RR은 뒤집힘(min 1000, max 0)이고 coxa_RM만 안 뒤집힘(min 0, max 1000)이다. 설정 파일 쪽이 어긋난 것으로 본다. 실물 코드에서 coxa_RM만 뒤집힘으로 바꿔 쓰면 된다 (로봇의 `rl_walk.py --fix-rm`도 같은 결론).
- 나머지 17개는 드라이버 각도 = URDF 각도.
- 다리 하나만 움직이는 바닥 시험은 회전이 0.01 rad 정도로 작다. 확정은 사람이 본 것으로 했다.

### 이상한 점

- **LF tibla 서보(ID 1)가 명령을 안 따른다.** 6개 같이 +0.1 명령: LF -0.017, 나머지 +0.075 ~ +0.088. 왼쪽만: LF +0.004, LM · LR +0.08. 바닥에서 다리가 눌린 상태라 그럴 수도 있으니 공중에서 따로 확인해야 한다 (미확인).
- 1절의 시작 자세 측정에서도 LF tibla만 -0.96으로 튀었다.
- 손목 카메라에는 다리가 안 보인다 (그리퍼 끝과 앞쪽 책상만 보임, `logs/20261111_wrist_rgb.png`).

### 몸 높이: URDF와 실물이 맞음

- 사람이 잰 값: 시작 자세에서 바닥 ~ 몸통 아래 **6 cm**.
- URDF 계산: base_link 원점이 몸통 메시 바닥(z -0.15 cm)과 거의 같다. 드라이버 각도(femur +0.88, tibla -0.82, coxa 0)를 넣으면 발끝(end_*)이 base_link보다 **6.0 cm** 아래다. 실측과 같다.
- 그러므로 드라이버 각도 = URDF 각도이고, 링크 길이도 맞다 (coxa_RM 부호만 예외).
- 처음에 "발이 몸보다 5 cm 위"라고 쓴 건 계산 실수였다. base_footprint(base_link보다 11.6 cm 아래의 기준점) 기준 높이를 base_link 기준으로 잘못 읽었다.
- **시뮬 기본자세(femur +0.10, tibla -0.12)는 발이 base_link보다 12 cm 아래다.** 시뮬 로봇은 몸을 12 cm 높이로 세우고 걷고, 실물은 6 cm로 낮게 웅크리고 선다. 발 간격(좌우 40 cm, 앞뒤 37 cm)은 둘이 비슷하다. 재학습 때 기본자세를 실물 값으로 바꿔야 한다.

### IMU 축 (바닥 시험으로 확인)

- 왼쪽 femur +0.1 (왼쪽이 내려감) → IMU x **+0.25**. 앞쪽 femur +0.1 (앞이 내려감) → IMU y **-0.26**.
- 그러므로 로봇 몸 기준 가속도 = (앞 IMU y, 왼쪽 -IMU x, 위 IMU z). 로봇의 `rl_walk.py` 변환 `base = [imu_y, -imu_x, imu_z]`와 같다. 자이로도 같은 변환 (coxa 시험에서 z 부호 확인).
- 가만히 서 있을 때 IMU y가 +0.8 → 몸 기준 앞쪽 가속도 +0.8, 즉 앞이 약 4.7° 들려 있다 (몸이 실제로 기운 건지 IMU가 기울게 달린 건지는 미확인).

## 3. LF tibla 서보(ID 1) 고장 (2026-11-11)

원본: `logs/20261111_floor_check.txt`의 step_response · LF tibla 항목.

- 굽히는 쪽(펄스 증가) 명령은 따르고, 펴는 쪽(펄스 감소) 명령은 크기 · 속도 · duration에 상관없이 안 따른다. 한 번 굽으면 다시 못 편다.
- 공중(손으로 든 상태)에서도, 자동 실행이 켜진 상태에서도, 재부팅 직후에도 같다. 재부팅하면 부팅 자세로 갈 때만 한 번 정상 자리(약 699 펄스)로 펴진다.
- 굽히는 쪽 반응 (서보 하나만 5 ms 간격으로 읽음): 명령 후 23 ms에 움직이기 시작, 148 ms에 90 % 도달, 최대 4.2 rad/s.
- 사람이 만져 보니 기어가 뻑뻑하다. 펴는 동작은 다리 무게나 몸무게를 거슬러야 하므로, 기어 마찰이나 힘 부족으로 펴는 쪽만 막히는 것으로 본다 (추정).
- 여분 서보 없음. 고치기 전에는 실물 걷기 시험 불가. 방법: 기어 청소 · 그리스, 같은 모델의 팔 서보와 임시 교체(ID 1로 바꾸고 0점 보정), 새 서보 주문.
- 추가 시험: 사용자가 서보 연결부를 풀었다 다시 조립 → 같음. 펴는 쪽으로 600 펄스까지 1.5초씩 반복 명령 → 1 펄스도 안 움직임. 토크 껐다 켜기 → 같음. 손으로 발끝을 바깥으로 살짝 밀며 펴기 명령 → 안 움직임.
- 서보 정보는 정상 서보(ID 7)와 같다: ID 응답 정상, 움직임 범위 0 ~ 1000, 전압 범위 4.5 ~ 14 V, 과열 보호 85 °C, 0점 보정 -11. 소프트웨어 설정 문제는 아니다.
- 서 있으면 몸무게에 밀려 계속 굽는다 (715 → 892 펄스). 이 상태로 오래 세워 두지 말 것.
- 캘리브레이션(0점 보정)은 기준점만 옮기므로 방향과 상관없이 막히는 이 문제는 못 고친다.

## 4. 서보 반응 속도 (2026-11-11, 손으로 들어 공중, 정상 다리)

스크립트: `step_response.py` (명령 1개 보내고 그 서보만 약 5 ms 간격으로 읽음, duration 0 = 최대 속도). 원본 CSV: `logs/step_*.csv`.

**왜:** 시뮬에는 명령 지연이 없다. 지연 시험(3-p)에서 100 ms까지는 버티고 150 ms에서 평지 실패했으므로 실제 값이 필요하다.

| 관절 | 계단 | 움직이기 시작 | 90 % 도착 | 최대 속도 |
|---|---|---|---|---|
| femur_RM | ±0.4 rad | 26 ~ 36 ms | 126 ~ 137 ms | 4.9 ~ 8.0 rad/s |
| tibla_RM | ±0.3 rad | 20 ~ 27 ms | 108 ~ 127 ms | 4.2 ~ 5.6 rad/s |
| tibla_LF (굽히는 쪽만) | -0.3 rad | 23 ms | 148 ms | 4.2 rad/s |

- 명령 후 움직이기 시작까지 약 20 ~ 36 ms. 다른 팀이 말한 50 ~ 150 ms는 도착 시간에 가깝다.
- 읽기 한 번이 약 5 ms 걸려서 시작 시간에는 그만큼 오차가 있다.
- 최대 속도는 시뮬 설정 6 rad/s와 비슷하다.
- 18개를 동시에 다룰 때는 읽기 50 ms가 더해지므로 따로 재야 한다 (제어 한 바퀴 시간, 아직 안 함).
- 결론 (사용자 판단): ID 1 서보 수리 또는 교체하기로 함. 그 전까지 실물 걷기 시험 보류.
